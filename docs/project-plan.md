# 北魏洛阳文献地图 GitHub 项目与网页设计方案

日期：2026-11-10  
状态：设计稿；本轮未创建远程仓库或发布网站。  
建议项目名：北魏洛阳文献地图 / Luoyang Documentary Atlas  
建议仓库名：luoyang-atlas

## 1. 推荐方案

采用一个 GitHub 仓库管理研究数据、制图代码和网站；使用 GitHub Actions 校验和构建，由 GitHub Pages 提供公开的静态网页；PDF、高清图和完整工作包通过 GitHub Releases 分版本下载。

网站第一目标是让读者完成一条完整路径：

看全城 → 进入区域 → 选择建筑群 → 阅读出处与校读 → 查看争议 → 分享固定版本的链接。

既有 v2.4 图册是第一批内容。网站与历史研究分别推进：网页改版不自动改变历史布局，历史证据更新可以单独形成新的研究版本。

推荐技术组合：Astro 静态页面、TypeScript、原生 SVG、d3-zoom、现有 Python 制图工具。浏览器使用构建时生成的 JSON；首期不需要服务器数据库、用户账号或地图服务密钥。GitHub Pages 支持 HTML/CSS/JavaScript 静态托管，Python 只能在构建阶段运行，不能作为 Pages 上的常驻服务。[1][5]

## 3. 网站页面结构

顶层导航控制在六项：

| 入口 | 主要用途 | 首版内容 |
|---|---|---|
| 首页 | 说明项目、识别版本、快速进入地图 | 项目说明、当前地图入口、最近更新 |
| 交互地图 | 全城探索和对象查询 | 缩放、拖动、11 区入口、搜索、实体高亮 |
| 分区图册 | 阅读已排版的成果 | R/D/S 系列，图例与附图分开归类 |
| 地点名录 | 不依赖地图查询对象 | 339 条记录、名称与别名、类别和静态详情 |
| 史料与争议 | 查看证据、解释和候选方案 | 版本目录、现有争议、宫前专题 |
| 版本与下载 | 引用和下载固定成果 | 研究版本、网页版本、PDF、SVG、高清包 |

地图页采用左侧控制、中央地图、右侧证据的桌面布局。顶栏常驻显示研究版本、盛时综合时层和“文献相对平面”。

左栏包括名称搜索、分区入口、类别图层、年代未定对象筛选、未定位名录及图例。中央提供放大、缩小、回全城、回本区和当前对象高亮。右栏由选择对象驱动，包含：

1. 规范名、原书写法、别名、T/P 等读图编号；
2. 当前场景使用的名称与状态；
3. 原文、版本、卷与页行定位；
4. 对原文的解释，以及据此采用的画法；
5. 方位、接邻、所属等关系；
6. 未决问题、关联争议和相关图页；
7. 固定版本链接及来源链接。

“来源、解释、画法”应分别显示。某个名称有据，并不同时说明院落边界、年代和道路侧别都已确定。

### 未定位对象

搜索未定位对象时，打开对应实体卡、名录或 E 系列说明，并显示“本版未落位”。不把它飞入任意一个地图位置。组名录可以高亮所属区域或相关组，但不能用组内排版顺序推导成员间距。

D01、D07、S06 包含地理栏与独立关系栏；网站应分别标注。整页不能当作一个可拼接地理视窗。

### 中文搜索

索引规范名、原书字形、繁简写法、经审查的异体、旧名、后改寺名和已有编号。原始文字保持不变；查询规范化只用于检索匹配。太尉府与太府寺等身份尚有争议的对象不自动合并。

339 条记录可先用浏览器中的轻量索引完成名称和别名检索；不急于引入全文检索服务。查原文全文是后续独立功能。

### 缩放层次、移动端与可访问性

低倍率突出城门、主要道路和主要建筑群；放大后显示细名与关系。不同类别保留文字图符，颜色不是唯一提示。

手机使用地图加底部详情抽屉，分区和图层另开面板。提供键盘可用的缩放与区域选择；通过普通 HTML 名录和详情页提供完整的替代阅读路径。关闭 JavaScript 时，仍能阅读区域目录、地点说明、静态缩略图和下载入口。

## 4. 地图技术选择

推荐直接使用 SVG，并用 d3-zoom 处理平移、滚轮缩放和触摸手势。d3-zoom 官方支持 SVG、HTML 和 Canvas，并支持程序化控制视图及缩放范围。[3]

当前约 192 KB 的共同母图适合作为首期实现基础；实际流畅度仍需在目标电脑、手机和网络条件下验证。这里的建议基于资产规模和复用成本，不把体积小直接等同于性能已达标。

需要增加的交互接口：

- 每个绘图对象有稳定 feature_id；
- 每个图形组有 data-feature-id，并通过映射表关联一个或多个实体；
- 按 temple、office、residence、market、road、water 等类别组织图层；
- 图外对象也有显示去向，但不生成世界坐标；
- 地区跳转使用既有视窗边界；
- 标签与高亮层不会改变原有定位点；
- 点击区域与可见线条区分处理，避免细线过难点击。

Leaflet CRS.Simple 可以作为未来多底图、瓦片或更复杂图层管理的备选。首期直接 SVG 更贴近当前材料，省去另一套坐标适配。若将来增加真正的地理配准，应使用独立字段和独立模式。

界面不显示公里比例尺、经纬度、定位按钮或路线距离。原文中的“一里”等距离继续保留为文字证据，不自动换算为当前绘图长度。

## 5. 数据结构

### 六个相互关联的部分

| 部分 | 保存什么 | 关键边界 |
|---|---|---|
| 版本与出处 sources | 书名、作者/校者、版本、数字转录来源、卷、篇目、页行、原文、链接、复用范围 | 书的版本与承载网页分别记录 |
| 实体 entities | 稳定身份、名称与别名、类别、编号、身份问题 | 不把一个时代名称永久绑定为唯一身份 |
| 断言 assertions | 有出处的最小关系及其解释 | 原始句法与标准化方向同时保留 |
| 事件 events | 立寺、改寺、塔始造、竣工、塔毁、迁居等 | 构件变化与整个建筑群变化分别记录 |
| 争议 disputes | 候选解释、证据、当前画法与未决问题 | “本版采用”与“历史已解决”分开 |
| 布局与视图 layouts/views | 绘图坐标、符号、区域裁切、关系栏、图层、方案 | 画面坐标不能反过来充当历史证据 |

所有引用保留稳定 ID。现有 ic_yongning 是永宁寺的实体 ID，T01 是读图编号，两者都保留。

### 一个实际迁移风险

现有永宁记录有 has_east → ic_taiwei，原句为“其寺東有太尉府”。标准化后，应表达为“ic_taiwei east_of ic_yongning”。若仅把字段 has_east 改名为 east_of 而不调整主客体，会使方向翻转。

“西对”“南界”“北邻”还带有面对、边界和接邻语义，不能全部压成一个没有区别的方位标签。

以下是拟议字段示例，尚未写入生产数据：

~~~json
{
  "id": "claim-yongning-taiwei-east",
  "subject_id": "ic_taiwei",
  "predicate": "east_of",
  "object_id": "ic_yongning",
  "evidence_kind": "explicit_text",
  "source_locator": "B12n0078_p0341a04-05",
  "original_subject_id": "ic_yongning",
  "original_relation": "has_east",
  "interpretation_note": "保留原关系，并以太尉府为主语标准化东向关系"
}
~~~

现有登记中 source_ref 与 source_locator 两种字段均需兼容；原始行码和显示层修正继续分别保存。

### 关系栏与地理画面的硬边界

拟设置：

- coordinate_system = documentary-layout；
- display_space = world / relationship_panel / appendix；
- placement_kind = point / approximate_area / relative_relation / unlocated；
- layout_id、scenario_id、variant_id；
- 支持该位置或关系的 assertion_ids。

世界坐标仅适用于 world 内的相应对象。关系栏和附录中的排版坐标只能服务排版。图形与实体使用多对多映射，避免把复合图符、组名录和道路别名拆成虚构地点。

### 时间与场景

当前场景标记为 documentary_composite，时间范围为 516 至 528 年河阴事件前。每个事件另外记录原始纪年、可确认的上下界和时间精度；未知就保留 unknown。

第一版使用“盛时综合图”场景入口。毁后图具备证据后，新增有明确日期或事件界限的场景。连续年份滑杆留待逐年状态有足够依据时再考虑。

塔毁、寺院废弃、用途改变、迁居和后续记载不明分别表示。“塔毁”不能自动让整座寺院消失，“未见后续记载”也不能自动变成毁灭状态。

### 迁移方式与唯一维护源

v2.4 原始文件先作为只读基线保存。用一次性适配器建立规范研究数据，核验完成后，以规范数据为日常维护源。旧快照用于比较，不再反向覆盖后续整理。

当前绘图程序通过兼容适配层读取规范数据，先复用已有渲染逻辑。生成的地图、索引和网页数据不手工改写，避免出现两份互相漂移的事实。

## 7. GitHub Pages 部署设计

建议项目站 URL 形式为：

https://OWNER.github.io/luoyang-atlas/

OWNER 是未来实际仓库所有者，以上不是已上线地址。项目站的默认地址包含仓库子路径。[1]

Astro 配置示例：

~~~javascript
import { defineConfig } from "astro/config";

export default defineConfig({
  output: "static",
  site: "https://OWNER.github.io",
  base: "/luoyang-atlas",
  trailingSlash: "always"
});
~~~

Astro 官方说明了 GitHub Pages 的静态部署、site 和 base 配置。页面内部链接及资源路径也必须遵守 base；仅设置配置字段并不能修复手写的根路径链接。[2]

地图页和每个实体详情页在构建时生成真实 HTML 路径。例如：

- /luoyang-atlas/map/
- /luoyang-atlas/places/ic_yongning/
- /luoyang-atlas/disputes/C01/

这样直接打开或刷新详情页也有对应文件。地图的视窗、选择对象等交互状态写入查询参数；不依赖服务器将任意地址重写为首页。Astro 支持构建时生成动态路由对应的静态页面。[8]

### 工作流划分

| 触发 | 工作 | 是否发布 |
|---|---|---|
| Pull request | 校验数据、构建网页、检查关键路径和地图样板 | 不部署正式站 |
| 合并到稳定 main | 生成网页产物，部署经审阅的当前网站 | 自动部署 Pages |
| 发布研究版本 | 生成完整图册、高清包、清单与校验值 | 更新 Release 与下载索引 |

GitHub 设置采用 Settings → Pages → Source → GitHub Actions。只把网站构建产物 site/dist 上传到 Pages，不把整个研究仓库当作站点根发布。

部署 job 按官方要求使用 pages:write、id-token:write，并依赖 build job、关联 github-pages environment。PR 校验仅需读取代码的权限。Actions 和运行时依赖在实施时核实版本、锁定并维护，不把文档示例中的“最新版”当成永久不变的版本。[4]

普通 PR 不会因此自动获得一个独立的公开预览站。第一阶段可提供构建产物、关键页面截图和本地预览供审阅；如确需在线分支预览，再单独设计。

### 制图构建与网页构建

将现有整册生成拆成两个入口：

- 网页导出：研究 JSON、可交互 SVG、视窗和搜索索引；
- 印刷导出：37 页 PDF、高清 PNG、完整工作包。

普通网页样式修改不重绘全部印刷文件。研究版本发行时再运行完整流程，并记录 Python、Inkscape、字体与依赖版本。网站下载索引指向已核验的对应 Release，不能依赖“最新文件”在构建时静默漂移。

## 8. 文件存放与平台边界

| 内容 | 放在哪里 |
|---|---|
| 研究数据、说明、代码、图符、配置 | Git 仓库 |
| 在线页面、优化 SVG、小型索引和缩略图 | Pages 成品 |
| PDF、高清总图、全部分图、完整工作包 | Release 附件 |
| 任务讨论、意见、复核过程 | Issues 与 Pull requests |
| 经采用的解释及其依据 | 回写仓库中的研究数据与说明 |

GitHub Releases 基于 tag，适合发布阶段成果并附带文件。当前约 31 MiB 的工作包可以作为 Release 附件；它也超过了浏览器直接向普通仓库上传文件的 25 MiB 限额。[6][7]

已核实的主要 Pages 限制是成品站不超过 1 GB、月带宽 100 GB 软限。自定义 Actions 工作流不受 Pages 每小时 10 次构建这一软限约束，但仍受其他平台资源规则约束。[9]

公开仓库可使用 GitHub Free 的 Pages。私有仓库可用性取决于套餐，仓库私有也不自动等于网站私有；本方案按公开研究成果站设计。[1][5]

代码、原创研究数据与图面、第三方资料分别记录许可及可展示范围。首版以自绘成果、整理后的解释、必要原文引用及来源链接为核心；现代校注全文、地图册扫描页和外部建筑照片按各自条件处理。

## 9. 版本管理和研究协作

### 两套版本号

- atlas-v2.4.0：研究数据、解释、布局和图册发行；
- web-v0.1.0：网站程序、交互和界面发行。

网页页脚同时显示二者。纯网页功能更新不迫使研究图册升级；历史关系或候选位置改变时，即使网站代码不动，也形成新的研究版本。

v2.1、v2.2、v2.3 和 v2.4 按实际能取得的原文件导入存档，登记真实导入日期和校验值，不制造过去已存在 Git 提交的历史。

### 固定版本链接

最新入口便于浏览，引用链接固定研究版本、场景、实体及必要的方案。例如拟采用：

/luoyang-atlas/atlas/v2.4/map/?entity=ic_yongning&region=R07&scenario=prosperity-composite&variant=baseline

该地址要求相应版本数据确实被保留和发布；若某旧版仅有图册下载，入口应明确说明，不能静默显示最新版。

### 争议协作

现有 C01—C30 可建立对应 Issue。Issue 负责讨论；disputes 数据和专题说明保存可发行的结论，两者相互链接。

争议记录包括：问题、受影响实体、原文和版本、候选 A/B、各自依据、对平面的影响、当前展示方案、待证问题、决策日期、相关 PR。

分别使用 display_decision 和 historical_resolution：为本版选择一种画法，不等于历史争议已经解决。

候选布局按一组相容的断言一起切换。不要把冲突位置平均，也不要允许任意组合开关拼出不可能同时成立的方案。

### 改动审阅

一次研究 PR 至少说明：

- 原文、版本或校注依据；
- 改动实体和断言；
- 对名称、位置、年代及图形分别有什么影响；
- 受影响区域与前后对照；
- 尚未解决的问题；
- 是否需要新的研究版本。

网页 PR 则说明用户行为变化和验证结果。两类改动可以关联，但审阅说明分别清楚。

## 12. 必要验证

数据检查聚焦真正会损害研究结果的问题：

1. 实体、断言、来源与图形映射引用完整；
2. 冻结基线校验值不变；
3. 关系栏和名录成员不生成伪地理坐标；
4. 方向关系转换与候选布局相容；
5. 年代未知不会被自动变成确定年代；
6. 研究发行能追溯到数据、布局、生成工具和 Git 提交。

网页验证聚焦真实访问：

- 在 /luoyang-atlas/ 子路径下打开，资源与链接正常；
- 直接访问、刷新实体页和固定版本链接正常；
- 桌面与手机能缩放、选区、读出处和退出详情；
- 一个已定位对象和一个未定位对象的行为均正确；
- 首屏不预载全部高清图册、完整工作包或整套大型中文字体；
- 上海网络条件与手机实际测试冷启动、重复访问和下载；
- 下载文件版本与页面显示版本一致。

性能目标是按需加载，首屏只取地图、必要索引和交互代码。具体体积与加载时间在首个可运行版本中测量后确定，不在设计稿中承诺尚未验证的访问速度。
